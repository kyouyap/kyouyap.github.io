# テストのアンチパターン

**このリファレンスを読むタイミング:** テストの作成・変更時、モックの追加時、または本番コードにテスト専用メソッドを追加したくなった時。

## 概要

テストは実際の動作を検証するものであり、モックの動作を検証するものではない。モックは分離の手段であり、テスト対象ではない。

**基本原則:** コードが何をするかをテストせよ。モックが何をするかではない。

**厳格な TDD に従えば、これらのアンチパターンは防げる。**

## 鉄の掟

```
1. モックの動作をテストしてはならない
2. 本番クラスにテスト専用メソッドを追加してはならない
3. 依存関係を理解せずにモックしてはならない
```

## アンチパターン 1: モックの動作をテストする

**違反例:**
```typescript
// BAD: モックの存在をテストしている
test('renders sidebar', () => {
  render(<Page />);
  expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
});
```

**なぜ問題か:**
- コンポーネントの動作ではなく、モックの動作を検証している
- モックが存在すれば通り、なければ失敗する
- 実際の動作について何もわからない

**人間のパートナーの指摘:** 「モックの動作をテストしていないか？」

**修正:**
```typescript
// GOOD: 本物のコンポーネントをテストするか、モックしない
test('renders sidebar', () => {
  render(<Page />);  // sidebar をモックしない
  expect(screen.getByRole('navigation')).toBeInTheDocument();
});

// もしくは分離のために sidebar をモックする必要がある場合:
// モックに対してアサートしない - sidebar がある状態での Page の動作をテストする
```

### ゲート関数

```
モック要素にアサートする前に:
  問い: 「本物のコンポーネントの動作をテストしているか、それともモックの存在だけか？」

  モックの存在をテストしている場合:
    やめろ - アサーションを削除するか、コンポーネントのモックを解除する

  代わりに実際の動作をテストする
```

## アンチパターン 2: 本番コードのテスト専用メソッド

**違反例:**
```typescript
// BAD: destroy() はテストでのみ使用
class Session {
  async destroy() {  // 本番 API に見える！
    await this._workspaceManager?.destroyWorkspace(this.id);
    // ... クリーンアップ
  }
}

// テスト内
afterEach(() => session.destroy());
```

**なぜ問題か:**
- 本番クラスがテスト専用コードで汚染される
- 本番で誤って呼び出される危険がある
- YAGNI と関心の分離に違反する
- オブジェクトのライフサイクルとエンティティのライフサイクルを混同している

**修正:**
```typescript
// GOOD: テストユーティリティがテストのクリーンアップを処理する
// Session には destroy() がない - 本番ではステートレス

// test-utils/ 内
export async function cleanupSession(session: Session) {
  const workspace = session.getWorkspaceInfo();
  if (workspace) {
    await workspaceManager.destroyWorkspace(workspace.id);
  }
}

// テスト内
afterEach(() => cleanupSession(session));
```

### ゲート関数

```
本番クラスにメソッドを追加する前に:
  問い: 「テストでしか使わないか？」

  はいの場合:
    やめろ - 追加しない
    テストユーティリティに置く

  問い: 「このクラスがこのリソースのライフサイクルを所有しているか？」

  いいえの場合:
    やめろ - このメソッドは間違ったクラスにある
```

## アンチパターン 3: 理解せずにモックする

**違反例:**
```typescript
// BAD: モックがテストロジックが依存する処理を破壊する
test('detects duplicate server', () => {
  // モックがテストが依存する設定書き込みを妨げる！
  vi.mock('ToolCatalog', () => ({
    discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
  }));

  await addServer(config);
  await addServer(config);  // throw すべきだが、しない！
});
```

**なぜ問題か:**
- モックされたメソッドにテストが依存する副作用があった（設定書き込み）
- 「安全のため」の過剰モックが実際の動作を壊す
- テストが間違った理由で通るか、不可解に失敗する

**修正:**
```typescript
// GOOD: 正しいレベルでモックする
test('detects duplicate server', () => {
  // 遅い部分をモックし、テストに必要な動作は保持する
  vi.mock('MCPServerManager'); // 遅いサーバー起動だけをモック

  await addServer(config);  // 設定が書き込まれる
  await addServer(config);  // 重複検出 ✓
});
```

### ゲート関数

```
メソッドをモックする前に:
  やめろ - まだモックしない

  1. 問い: 「本物のメソッドにはどんな副作用があるか？」
  2. 問い: 「このテストはそれらの副作用に依存しているか？」
  3. 問い: 「このテストが何を必要としているか完全に理解しているか？」

  副作用に依存している場合:
    より低いレベルでモック（実際の遅い/外部の操作）
    または必要な動作を保持するテストダブルを使う
    テストが依存する高レベルメソッドをモックしない

  テストが何に依存しているか不明な場合:
    まず本物の実装でテストを実行する
    実際に何が起きる必要があるかを観察する
    その後、適切なレベルで最小限のモックを追加する

  危険信号:
    - 「安全のためにモックしよう」
    - 「遅いかもしれない、モックした方がいい」
    - 依存チェーンを理解せずにモックする
```

## アンチパターン 4: 不完全なモック

**違反例:**
```typescript
// BAD: 部分的なモック - 必要だと思うフィールドだけ
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Alice' }
  // 不足: 下流のコードが使う metadata
};

// 後で: コードが response.metadata.requestId にアクセスして壊れる
```

**なぜ問題か:**
- **部分的なモックは構造的な前提を隠す** - 知っているフィールドだけモックした
- **下流のコードが含めなかったフィールドに依存する可能性がある** - サイレントな失敗
- **テストは通るが結合テストで失敗する** - モックは不完全、本物の API は完全
- **偽の信頼感** - テストは実際の動作について何も証明しない

**鉄の掟:** 直接のテストが使うフィールドだけでなく、現実に存在する完全なデータ構造をモックせよ。

**修正:**
```typescript
// GOOD: 本物の API の完全性を反映する
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Alice' },
  metadata: { requestId: 'req-789', timestamp: 1234567890 }
  // 本物の API が返す全フィールド
};
```

### ゲート関数

```
モックレスポンスを作成する前に:
  確認: 「本物の API レスポンスにはどんなフィールドがあるか？」

  アクション:
    1. ドキュメント/サンプルから実際の API レスポンスを調べる
    2. システムが下流で消費する可能性のある全フィールドを含める
    3. モックが本物のレスポンススキーマと完全に一致することを検証する

  重要:
    モックを作る場合、構造全体を理解する必要がある
    部分的なモックは、省略されたフィールドにコードが依存するとサイレントに失敗する

  不確かな場合: 文書化されている全フィールドを含める
```

## アンチパターン 5: 後回しの結合テスト

**違反例:**
```
✅ 実装完了
❌ テスト未作成
「テスト準備完了」
```

**なぜ問題か:**
- テストは実装の一部であり、オプションのフォローアップではない
- TDD ならこれを防げた
- テストなしに完了を主張できない

**修正:**
```
TDD サイクル:
1. 失敗するテストを書く
2. 通る実装を書く
3. リファクタリング
4. その後で完了を主張する
```

## モックが複雑になりすぎた時

**警告サイン:**
- モックのセットアップがテストロジックより長い
- テストを通すために全てをモックしている
- モックに本物のコンポーネントが持つメソッドがない
- モックを変更するとテストが壊れる

**人間のパートナーの問い:** 「ここでモックを使う必要があるか？」

**検討:** 複雑なモックより本物のコンポーネントを使った結合テストの方がシンプルなことが多い

## TDD がこれらのアンチパターンを防ぐ理由

**TDD が役立つ理由:**
1. **テストを先に書く** → 実際に何をテストしているか考えることを強制する
2. **失敗を確認する** → テストがモックではなく実際の動作をテストしていることを確認する
3. **最小限の実装** → テスト専用メソッドが忍び込まない
4. **本物の依存関係** → モックする前にテストが実際に何を必要としているかがわかる

**モックの動作をテストしているなら、TDD に違反している** - 本物のコードに対してテストの失敗を見る前にモックを追加した。

## クイックリファレンス

| アンチパターン | 修正 |
|--------------|------|
| モック要素にアサートする | 本物のコンポーネントをテストするかモックを解除する |
| 本番コードのテスト専用メソッド | テストユーティリティに移す |
| 理解せずにモック | まず依存関係を理解し、最小限のモックにする |
| 不完全なモック | 本物の API を完全に反映する |
| 後回しのテスト | TDD - テストファースト |
| 過度に複雑なモック | 結合テストを検討する |

## 危険信号

- `*-mock` テスト ID に対するアサーション
- テストファイルでのみ呼ばれるメソッド
- モックのセットアップがテストの50%超
- モックを除去するとテストが失敗する
- モックが必要な理由を説明できない
- 「安全のため」のモック

## 結論

**モックは分離のためのツールであり、テスト対象ではない。**

TDD がモックの動作をテストしていることを明らかにしたなら、道を誤っている。

修正: 実際の動作をテストするか、そもそもなぜモックしているかを問い直せ。
