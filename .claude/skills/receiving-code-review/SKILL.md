# コードレビューの受け取り

## 概要

コードレビューに求められるのは技術的評価であり、感情的パフォーマンスではない。

**基本原則:** 実装前に検証せよ。仮定する前に質問せよ。社会的快適さより技術的正確さ。

## 対応パターン

```
コードレビューのフィードバックを受けた時:

1. 読む: フィードバック全体を反応せずに読む
2. 理解: 要件を自分の言葉で言い換える（または質問する）
3. 検証: コードベースの現実と照合する
4. 評価: このコードベースにとって技術的に妥当か？
5. 対応: 技術的な確認または根拠ある反論
6. 実装: 1項目ずつ、各々テスト
```

## 禁止される応答

**してはならないこと:**
- 「おっしゃる通りです！」（明示的な CLAUDE.md 違反）
- 「良い指摘です！」/「素晴らしいフィードバック！」（パフォーマンス的）
- 「今すぐ実装します」（検証前に）

**代わりに:**
- 技術的要件を言い換える
- 明確化の質問をする
- 間違っている場合は技術的根拠で反論する
- ただ作業に取り掛かる（言葉より行動）

## 不明確なフィードバックへの対応

```
いずれかの項目が不明確な場合:
  やめろ - まだ何も実装しない
  不明確な項目の明確化を求める

理由: 項目は関連している可能性がある。部分的な理解 = 間違った実装。
```

**例:**
```
人間のパートナー: 「1-6 を修正して」
1,2,3,6 は理解。4,5 が不明確。

❌ 間違い: 1,2,3,6 を今すぐ実装し、4,5 は後で聞く
✅ 正解: 「1,2,3,6 は理解しました。4 と 5 について着手前に明確化が必要です。」
```

## 出所別の対応

### 人間のパートナーから
- **信頼する** - 理解した上で実装
- スコープが不明な場合は**質問する**
- **パフォーマンス的同意は不要**
- **行動に移す**か技術的確認のみ

### 外部レビュアーから
```
実装前に:
  1. 確認: このコードベースにとって技術的に正しいか？
  2. 確認: 既存機能を壊さないか？
  3. 確認: 現在の実装の理由は？
  4. 確認: 全プラットフォーム/バージョンで動作するか？
  5. 確認: レビュアーは完全なコンテキストを理解しているか？

提案が間違っていそうな場合:
  技術的根拠で反論する

容易に検証できない場合:
  そう伝える: 「[X] がないと検証できません。[調査/質問/進行] しますか？」

人間のパートナーの過去の判断と矛盾する場合:
  まず人間のパートナーと相談する
```

**人間のパートナーのルール:** 「外部フィードバック - 懐疑的であれ、ただし慎重に確認せよ」

## 「プロフェッショナルな」機能への YAGNI チェック

```
レビュアーが「適切に実装」を提案した場合:
  コードベースで実際の使用を grep する

  未使用の場合: 「このエンドポイントは呼ばれていません。削除しますか (YAGNI)？」
  使用中の場合: 適切に実装する
```

**人間のパートナーのルール:** 「あなたとレビュアーの両方が私に報告する。この機能が不要なら、追加しない。」

## 実装順序

```
複数項目のフィードバックの場合:
  1. 不明確なものをまず全て明確化する
  2. この順序で実装する:
     - ブロッキング問題（破壊、セキュリティ）
     - 単純な修正（タイプミス、import）
     - 複雑な修正（リファクタリング、ロジック）
  3. 各修正を個別にテスト
  4. リグレッションがないか検証
```

## 反論すべきタイミング

反論すべき場合:
- 提案が既存機能を壊す
- レビュアーが完全なコンテキストを持っていない
- YAGNI に違反する（未使用機能）
- このスタックにとって技術的に不正確
- レガシー/互換性の理由がある
- 人間のパートナーのアーキテクチャ判断と矛盾する

**反論の仕方:**
- 防衛的ではなく技術的根拠を使う
- 具体的な質問をする
- 動作するテスト/コードを参照する
- アーキテクチャに関わる場合は人間のパートナーを巻き込む

**声に出して反論しにくい場合のシグナル:** "Strange things are afoot at the Circle K"

## 正しいフィードバックの認め方

フィードバックが正しい場合:
```
✅ 「修正済み。[何を変更したかの簡潔な説明]」
✅ 「良い指摘 - [具体的な問題]。[場所] で修正済み。」
✅ [ただ修正してコードで示す]

❌ 「おっしゃる通りです！」
❌ 「良い指摘です！」
❌ 「見つけていただきありがとうございます！」
❌ 「[何であれ] ありがとうございます」
❌ いかなる感謝表現も
```

**感謝不要の理由:** 行動で示す。ただ修正する。コード自体がフィードバックを受け取ったことを示す。

**「ありがとう」と書きそうになったら:** 削除する。代わりに修正内容を述べる。

## 反論を訂正する場合

反論して間違っていた場合:
```
✅ 「あなたが正しかった - [X] を確認したら [Y] でした。今から実装します。」
✅ 「検証した結果、正しいです。最初の理解が間違っていた理由は [理由]。修正中。」

❌ 長い謝罪
❌ 反論した理由を弁護する
❌ 過剰な説明
```

訂正を事実として述べ、先に進む。

## よくある間違い

| 間違い | 修正 |
|--------|------|
| パフォーマンス的同意 | 要件を述べるか、ただ行動する |
| 盲目的実装 | まずコードベースで検証する |
| テストなしのバッチ処理 | 1つずつ、各々テスト |
| レビュアーが正しいと思い込む | 壊れないか確認する |
| 反論を避ける | 技術的正確さ > 快適さ |
| 部分的な実装 | まず全項目を明確化する |
| 検証できないのに進む | 制限を述べ、方向を求める |

## 実例

**パフォーマンス的同意（悪い例）:**
```
レビュアー: 「レガシーコードを削除して」
❌ 「おっしゃる通りです！ 削除しますね...」
```

**技術的検証（良い例）:**
```
レビュアー: 「レガシーコードを削除して」
✅ 「確認中... ビルドターゲットは 10.15+、この API は 13+ が必要。後方互換のためレガシーが必要です。現在の実装は bundle ID が間違っています - 修正しますか、それとも pre-13 サポートを廃止しますか？」
```

**YAGNI（良い例）:**
```
レビュアー: 「データベース、日付フィルター、CSV エクスポート付きの適切なメトリクス追跡を実装して」
✅ 「コードベースを grep しました - このエンドポイントを呼んでいるものはありません。削除しますか (YAGNI)？ それとも見落としている使用箇所がありますか？」
```

**不明確な項目（良い例）:**
```
人間のパートナー: 「1-6 を修正して」
1,2,3,6 は理解。4,5 が不明確。
✅ 「1,2,3,6 は理解しました。実装前に 4 と 5 の明確化が必要です。」
```

## GitHub スレッドへの返信

GitHub のインラインレビューコメントに返信する際は、トップレベルの PR コメントではなく、コメントスレッド内で返信する（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`）。

## 結論

**外部フィードバック = 評価すべき提案であり、従うべき命令ではない。**

検証。質問。そして実装。

パフォーマンス的同意は不要。常に技術的厳密さ。
