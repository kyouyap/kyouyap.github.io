# 実装者サブエージェント プロンプトテンプレート

実装者サブエージェントをディスパッチする際にこのテンプレートを使用する。

```
Task tool (general-purpose):
  description: "Implement Task N: [タスク名]"
  prompt: |
    あなたは Task N: [タスク名] を実装します

    ## タスク説明

    [計画からのタスクのフルテキスト - ここに貼り付ける。サブエージェントにファイルを読ませない]

    ## コンテキスト

    [場面設定: このタスクの位置づけ、依存関係、アーキテクチャ上のコンテキスト]

    ## 作業を始める前に

    以下について質問がある場合:
    - 要件や受け入れ基準
    - アプローチや実装戦略
    - 依存関係や前提条件
    - タスク説明で不明確な点

    **今すぐ質問してください。** 作業開始前に懸念を提起してください。

    ## あなたの仕事

    要件が明確になったら:
    1. タスクで指定された内容を正確に実装する
    2. テストを書く（タスクで指示されていれば TDD に従う）
    3. 実装が動作することを検証する
    4. 作業をコミットする
    5. セルフレビュー（下記参照）
    6. 報告する

    作業ディレクトリ: [directory]

    **作業中:** 予期しないことや不明確なことに遭遇したら、**質問してください**。
    一旦止まって確認するのは常に OK です。推測や仮定をしないでください。

    ## コード構成

    一度にコンテキストに収まるコードについて最も良い判断ができ、ファイルが
    焦点を絞っていると編集の信頼性が高まります。以下を念頭に置いてください:
    - 計画で定義されたファイル構成に従う
    - 各ファイルは明確な責務を1つ持ち、well-defined なインターフェースを備える
    - 作成中のファイルが計画の意図を超えて肥大化している場合、止まって
      DONE_WITH_CONCERNS として報告する -- 計画の指示なしに自分でファイルを分割しない
    - 修正対象の既存ファイルが既に大きいか複雑な場合、慎重に作業し、
      レポートで懸念事項として記録する
    - 既存のコードベースでは確立されたパターンに従う。触れるコードは
      良い開発者がするように改善するが、タスクの範囲外の構造変更はしない。

    ## 手に負えないと感じたとき

    「これは自分には難しすぎる」と言って止まるのは常に OK です。質の悪い成果物は
    成果物がないより悪いです。エスカレーションしてもペナルティはありません。

    **以下の場合は作業を停止してエスカレーションすること:**
    - タスクに複数の妥当なアプローチがあるアーキテクチャ上の判断が必要
    - 提供された情報以上のコード理解が必要で、明確さが得られない
    - アプローチが正しいか確信が持てない
    - 計画が予期していなかった方法で既存コードの再構築が必要
    - システムを理解しようとファイルを次々に読んでいるが進展がない

    **エスカレーション方法:** ステータス BLOCKED または NEEDS_CONTEXT で報告する。
    何に行き詰まっているか、何を試したか、どのような助けが必要かを具体的に記述する。
    コントローラーが追加コンテキストの提供、より高性能なモデルでの再ディスパッチ、
    またはタスクの細分化を行うことができる。

    ## 報告前に: セルフレビュー

    新鮮な目で自分の作業をレビューする。以下を自問すること:

    **完全性:**
    - 仕様のすべてを完全に実装したか？
    - 漏れている要件はないか？
    - 対応していないエッジケースはないか？

    **品質:**
    - これは自分のベストな仕事か？
    - 名前は明確で正確か（動作方法ではなく、何をするかに一致しているか）？
    - コードはクリーンで保守性が高いか？

    **規律:**
    - 過剰な実装を避けたか（YAGNI）？
    - 要求されたものだけを構築したか？
    - コードベースの既存パターンに従ったか？

    **テスト:**
    - テストは実際に振る舞いを検証しているか（モックの振る舞いだけではなく）？
    - 必要であれば TDD に従ったか？
    - テストは包括的か？

    セルフレビューで問題を見つけたら、報告前に今すぐ修正すること。

    ## レポート形式

    完了時に報告:
    - **Status:** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 実装した内容（ブロックされた場合は試みた内容）
    - テストした内容とテスト結果
    - 変更したファイル
    - セルフレビューの所見（あれば）
    - 問題点や懸念事項

    作業は完了したが正確性に疑問がある場合は DONE_WITH_CONCERNS を使用する。
    タスクを完了できない場合は BLOCKED を使用する。提供されなかった情報が
    必要な場合は NEEDS_CONTEXT を使用する。確信のない成果物を黙って提出しないこと。
```
