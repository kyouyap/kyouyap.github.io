# Systematic Debugging

## 概要

場当たり的な修正は時間を浪費し、新たなバグを生む。その場しのぎのパッチは根本的な問題を覆い隠すだけ。

**基本原則:** 修正を試みる前に必ず root cause を特定すること。症状の修正は失敗である。

**このプロセスの文面を破ることは、デバッグの精神を破ることである。**

## 鉄則

```
ROOT CAUSE の調査なしに修正を行ってはならない
```

Phase 1 を完了していなければ、修正を提案してはならない。

## いつ使うか

あらゆる技術的問題に使用する:

- テスト失敗
- 本番環境のバグ
- 予期しない挙動
- パフォーマンス問題
- ビルド失敗
- 統合の問題

**特に以下の場合に使うこと:**

- 時間的プレッシャーがあるとき（緊急時ほど推測に頼りがち）
- 「ちょっとした修正で直りそう」と思えるとき
- 既に複数の修正を試みたとき
- 前回の修正がうまくいかなかったとき
- 問題を完全に理解できていないとき

**スキップしてはならないとき:**

- 問題が単純に見えるとき（単純なバグにも root cause はある）
- 急いでいるとき（急げば手戻りが確定する）
- マネージャーが「今すぐ直せ」と言っているとき（体系的アプローチの方が場当たり的な対応より速い）

## 4つのフェーズ

各フェーズを完了してから次に進むこと。

### Phase 1: Root Cause の調査

**修正を試みる前に:**

1. **エラーメッセージを注意深く読む**
   - エラーや警告を読み飛ばさない
   - 正確な解決策が含まれていることが多い
   - stack trace を最後まで読む
   - 行番号、ファイルパス、エラーコードを記録する

2. **一貫した再現手順を確認する**
   - 確実にトリガーできるか？
   - 正確な手順は？
   - 毎回発生するか？
   - 再現できない場合 → データを収集する、推測しない

3. **最近の変更を確認する**
   - この問題を引き起こした変更は何か？
   - git diff、最近のコミット
   - 新しい依存関係、設定変更
   - 環境の違い

4. **マルチコンポーネントシステムでの証拠収集**

   **システムが複数のコンポーネントを持つ場合（CI → ビルド → 署名、API → サービス → データベース）:**

   **修正を提案する前に、診断用の計装を追加する:**

   ```
   各コンポーネント境界に対して:
     - コンポーネントに入るデータをログ出力
     - コンポーネントから出るデータをログ出力
     - 環境・設定の伝搬を検証
     - 各レイヤーでの状態を確認

   一度実行して、どこで壊れるかを示す証拠を収集
   次に証拠を分析して障害コンポーネントを特定
   次にその特定のコンポーネントを調査
   ```

   **例（多層システム）:**

   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **これにより判明すること:** どのレイヤーが失敗しているか（secrets → workflow ✓、workflow → build ✗）

5. **データフローの追跡**

   **エラーが call stack の深い位置にある場合:**

   このディレクトリの `root-cause-tracing.md` に完全な逆方向トレース技法がある。

   **簡易版:**
   - 不正な値はどこで発生しているか？
   - 何がこの不正な値を渡して呼び出したか？
   - ソースが見つかるまで上方向に追跡を続ける
   - 症状ではなくソースで修正する

### Phase 2: パターン分析

**修正の前にパターンを見つける:**

1. **動作する例を探す**
   - 同じコードベース内の類似した動作コードを見つける
   - 壊れているものに似ていて動作しているものは何か？

2. **リファレンスと比較する**
   - パターンを実装する場合、リファレンス実装を完全に読む
   - 流し読みしない - すべての行を読む
   - パターンを完全に理解してから適用する

3. **差分を特定する**
   - 動作しているものと壊れているもの、何が違うか？
   - どんなに小さくてもすべての差分をリストアップ
   - 「それは関係ないだろう」と決めつけない

4. **依存関係を把握する**
   - 他にどのコンポーネントが必要か？
   - どの設定、構成、環境が必要か？
   - どのような前提条件があるか？

### Phase 3: 仮説とテスト

**科学的手法:**

1. **単一の仮説を立てる**
   - 明確に述べる: 「Yという理由で、Xが root cause だと考える」
   - 書き留める
   - 曖昧ではなく具体的に

2. **最小限のテストを行う**
   - 仮説を検証するための最小限の変更を行う
   - 一度に一つの変数だけ
   - 複数の修正を同時に行わない

3. **続行する前に検証する**
   - うまくいったか？ はい → Phase 4
   - うまくいかなかったか？ 新しい仮説を立てる
   - さらに修正を積み重ねない

4. **わからないとき**
   - 「Xがわからない」と言う
   - わかったふりをしない
   - 助けを求める
   - もっと調べる

### Phase 4: 実装

**症状ではなく root cause を修正する:**

1. **失敗するテストケースを作成する**
   - 可能な限りシンプルな再現
   - 可能であれば自動テスト
   - フレームワークがなければワンオフのテストスクリプト
   - 修正前に必ず作成すること
   - 適切な失敗テストの書き方は `test-driven-development` スキルを使用

2. **単一の修正を実装する**
   - 特定された root cause に対処する
   - 一度に一つの変更
   - 「ついでに」の改善はしない
   - リファクタリングをバンドルしない

3. **修正を検証する**
   - テストは通るか？
   - 他のテストが壊れていないか？
   - 問題は実際に解決したか？

4. **修正がうまくいかない場合**
   - 止まる
   - 数える: 何回修正を試みたか？
   - 3回未満: Phase 1 に戻り、新しい情報で再分析
   - **3回以上: 止まってアーキテクチャを疑う（下記ステップ5）**
   - アーキテクチャの議論なしに4回目の修正を試みない

5. **3回以上の修正が失敗した場合: アーキテクチャを疑う**

   **アーキテクチャの問題を示すパターン:**
   - 各修正が新たな共有状態/結合/異なる場所の問題を明らかにする
   - 修正に「大規模なリファクタリング」が必要
   - 各修正が別の場所で新たな症状を生む

   **立ち止まって根本を問い直す:**
   - このパターンは根本的に正しいか？
   - 「惰性で続けている」だけではないか？
   - 症状の修正を続けるのではなく、アーキテクチャをリファクタリングすべきか？

   **さらなる修正を試みる前に、人間のパートナーと議論すること**

   これは仮説の失敗ではない - アーキテクチャの間違いである。

## 危険信号 - 止まってプロセスに従う

以下のように考えている自分に気づいたら:

- 「今はとりあえず直して、後で調べよう」
- 「Xを変えてみて、うまくいくか試そう」
- 「複数の変更を入れてテストを実行しよう」
- 「テストは省略して、手動で確認しよう」
- 「たぶんXだろう、それを直そう」
- 「完全にはわからないけど、これでうまくいくかも」
- 「パターンはXと言っているが、別のやり方で適用しよう」
- 「主な問題はこれ: [調査なしで修正をリスト]」
- データフローを追跡する前に解決策を提案する
- **「もう一回修正を試そう」（既に2回以上試みた後）**
- **各修正が異なる場所で新たな問題を明らかにする**

**上記すべてに該当: 止まる。Phase 1 に戻る。**

**3回以上の修正が失敗した場合:** アーキテクチャを疑う（Phase 4.5 参照）

## 人間のパートナーからの「やり方を間違えている」サイン

**以下のリダイレクションに注意:**

- 「それは起きていないのでは？」 - 検証せずに仮定している
- 「それで…がわかるの？」 - 証拠収集を追加すべきだった
- 「推測をやめて」 - 理解なしに修正を提案している
- 「Ultrathink して」 - 症状ではなく根本を問い直す
- 「行き詰まった？」（フラストレーション気味に） - アプローチがうまくいっていない

**これらを見たら:** 止まる。Phase 1 に戻る。

## よくある言い訳

| 言い訳                                               | 現実                                                                 |
| ---------------------------------------------------- | -------------------------------------------------------------------- |
| 「問題は単純だから、プロセスは不要」                 | 単純な問題にも root cause はある。単純なバグならプロセスも速い。     |
| 「緊急事態で、プロセスをやる時間がない」             | 体系的デバッグは推測と試行錯誤の繰り返しより速い。                   |
| 「まずこれを試して、それから調べよう」               | 最初の修正がパターンを決める。最初から正しくやること。               |
| 「修正が効くか確認してからテストを書こう」           | テストなしの修正は定着しない。テストが先であることを証明する。       |
| 「複数の修正を一度にやれば時間節約」                 | 何が効いたか分離できない。新たなバグを生む。                         |
| 「リファレンスが長すぎるので、パターンを適用しよう」 | 部分的な理解はバグを保証する。完全に読むこと。                       |
| 「問題が見えた、直そう」                             | 症状が見えること ≠ root cause の理解。                               |
| 「もう一回修正を試そう」（2回以上失敗後）            | 3回以上の失敗 = アーキテクチャの問題。パターンを疑い、再修正しない。 |

## クイックリファレンス

| フェーズ          | 主な活動                                               | 成功基準                       |
| ----------------- | ------------------------------------------------------ | ------------------------------ |
| **1. Root Cause** | エラーを読む、再現する、変更を確認する、証拠を収集する | 何が起きているか、なぜかを理解 |
| **2. パターン**   | 動作する例を探す、比較する                             | 差分を特定                     |
| **3. 仮説**       | 理論を立てる、最小限でテスト                           | 確認済み、または新たな仮説     |
| **4. 実装**       | テスト作成、修正、検証                                 | バグ解決、テスト通過           |

## プロセスで「Root Cause なし」と判明した場合

体系的な調査の結果、問題が本当に環境依存、タイミング依存、または外部要因の場合:

1. プロセスを完了している
2. 調査した内容を文書化する
3. 適切なハンドリングを実装する（リトライ、タイムアウト、エラーメッセージ）
4. 今後の調査のためにモニタリング/ログを追加する

**ただし:** 「root cause なし」のケースの95%は調査不足である。

## 補助テクニック

以下のテクニックは systematic debugging の一部であり、このディレクトリで利用可能:

- **`root-cause-tracing.md`** - call stack を逆方向にたどってバグの発生源を見つける
- **`defense-in-depth.md`** - root cause 発見後に複数レイヤーでバリデーションを追加する
- **`condition-based-waiting.md`** - 任意のタイムアウトを条件ポーリングに置き換える

**関連スキル:**

- **test-driven-development** - 失敗するテストケースの作成に使用（Phase 4、ステップ1）
- **verification-before-completion** - 成功を主張する前に修正が機能したか検証

## 実際の効果

デバッグセッションからの実績:

- 体系的アプローチ: 15〜30分で修正
- 場当たり的な修正アプローチ: 2〜3時間の試行錯誤
- 一発修正率: 95% vs 40%
- 新たなバグの発生: ほぼゼロ vs 頻繁
