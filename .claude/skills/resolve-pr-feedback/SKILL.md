# PR レビューフィードバックの一括解決

## 概要

PR のレビューコメントを全件自律的に処理し、実装・テスト・プッシュ・返信まで完遂する。

**中核原則:** 全コメント処理。質問禁止。自律判断。証拠で検証。

**開始時に宣言:** "resolve-pr-feedback スキルを使って PR #<NUMBER> の全レビューコメントを処理します。"

## 使用タイミング

**使うとき:**
- PR にレビューコメントがあり一括処理したいとき
- レビュアーのフィードバックを質問せず全て実装したいとき
- CI を通した上でプッシュまで自律完了したいとき

**使わないとき:**
- フィードバックの技術的正当性を批判的に評価したいとき → `receiving-code-review`
- 1 件だけの軽微な修正 → 直接修正で十分
- アーキテクチャの根本変更を含む指摘 → 人間パートナーと相談

## 既存スキルとの差別化

| 観点 | receiving-code-review | resolve-pr-feedback |
|------|----------------------|---------------------|
| 目的 | フィードバックの批判的評価 | 全件自律実行 |
| 質問 | 不明点は必ず質問 | 質問禁止、自律判断 |
| 押し返し | 技術的に不適切なら押し返す | 基本的に全て実装 |
| スコープ | 1 件ずつ慎重に | 一括処理 |

## プロセス

### ステップ 0: worktree の準備 (必須)

**REQUIRED SUB-SKILL:** `using-git-worktrees` を使用する。

PR ブランチで作業するための worktree を準備する:

1. PR のブランチ名を取得:
```bash
gh pr view <NUMBER> --json headRefName --jq '.headRefName'
```

2. 既存 worktree の確認: `git worktree list` で同じブランチの worktree が既にあるか確認
   - **既にある場合:** その worktree ディレクトリに移動して再利用する
   - **ない場合:** `using-git-worktrees` スキルに従い新規作成

3. worktree 内で PR ブランチが正しくチェックアウトされていることを確認:
```bash
git branch --show-current
```

4. 依存関係をインストール:
```bash
cd frontend && pnpm install
```

5. テストベースラインを確認:
```bash
cd frontend && pnpm run typecheck && pnpm run test:ci
```

**worktree 内にいることを確認せずにステップ 1 以降に進んではならない。**

### ステップ 1: 環境情報の取得

```bash
gh repo view --json owner,name --jq '"\(.owner.login)/\(.name)"'
git branch --show-current
```

リポジトリの owner/name と現在のブランチを記録する。以降の API 呼び出しで使用。

### ステップ 2: 全レビューコメントの取得

2 つのソースからコメントを取得する（両方必須）:

```bash
# PR レビューコメント（インラインコメント含む）
gh api repos/{owner}/{repo}/pulls/<NUMBER>/comments

# PR 本文コメントとレビューサマリ
gh pr view <NUMBER> --json reviews,comments
```

**漏れ防止:** 片方だけではコメントが欠落する。必ず両方から取得。

### ステップ 3: コメントの分類と優先順位付け

全コメントを以下の 4 カテゴリに分類:

| カテゴリ | 説明 | 対応 |
|----------|------|------|
| **actionable** | 具体的な変更要求 | 実装する |
| **question** | レビュアーからの質問 | コードから回答を導出して返信 |
| **praise** | 肯定的コメント | 返信不要（またはスキップ） |
| **resolved** | 既に解決済み | 確認して返信 |

**実装順序:**
1. ブロッキング問題（ビルド破壊、セキュリティ）
2. 簡単な修正（タイポ、インポート、命名）
3. 複雑な修正（ロジック変更、リファクタリング）
4. question への回答

### ステップ 4: 各コメントの実装

コメントごとに以下を実行:

```
1. READ: 対象ファイルを読み、コメントの文脈を理解
2. UNDERSTAND: 変更要求の意図を把握
3. IMPLEMENT: 変更を実装
4. STAGE: 変更をステージング (git add)
```

**1 コメント = 1 論理単位。** 関連する変更はまとめてよいが、無関係な変更は混ぜない。

### ステップ 5: テスト・lint・修正サイクル

CI と同一のコマンドを実行:

```bash
cd frontend && pnpm run typecheck
cd frontend && pnpm run lint
cd frontend && pnpm run format:check
cd frontend && pnpm run test:ci
```

**失敗した場合:**
1. エラー出力を読む
2. 修正する
3. 再実行する
4. 全てパスするまで繰り返す

**全コマンドがパスしないままステップ 6 に進んではならない。**

### ステップ 6: コミットとプッシュ

```bash
git add -A
git commit -m "$(cat <<'EOF'
fix: PR #<NUMBER> レビューフィードバックを反映

- <変更1の概要>
- <変更2の概要>
- <変更Nの概要>
EOF
)"
git push
```

**コミットメッセージ:**
- プレフィックスは `fix:` を使用
- 本文に全変更の概要を箇条書き
- 各行は具体的に（「コメント対応」のような曖昧な記述は禁止）

### ステップ 7: GitHub 上でコメントに返信

各 actionable / question コメントに個別返信:

```bash
# インラインコメント（review comment）への返信
gh api repos/{owner}/{repo}/pulls/<NUMBER>/comments/<COMMENT_ID>/replies \
  -f body="Fixed. <具体的な変更内容>"

# PR 本文コメントへの返信
gh pr comment <NUMBER> --body "<内容>"
```

**返信ルール:**
- 簡潔に変更内容を記述（"Fixed. ..." / "Addressed. ..."）
- パフォーマンス的同意や感謝表現は禁止
- question には調査結果を事実として回答
- praise には返信不要

### ステップ 8: 最終サマリの提示

全コメントの処理結果をテーブル形式で報告:

```
| # | コメント概要 | カテゴリ | 対応 | ステータス |
|---|-------------|----------|------|-----------|
| 1 | 変数名の修正 | actionable | 変数名を camelCase に統一 | ✅ 完了 |
| 2 | テストの追加 | actionable | ユニットテスト追加 | ✅ 完了 |
| 3 | 良い実装ですね | praise | — | ⏭️ スキップ |
| 4 | この関数の意図は？ | question | コードから回答を返信 | ✅ 回答済 |

検証結果:
- typecheck: ✅ パス
- lint: ✅ パス
- format:check: ✅ パス
- test:ci: ✅ パス (XX tests)

コミット: <SHA> → pushed to <branch>
```

## 曖昧なコメントの判断ルール

質問禁止のため、曖昧なコメントは以下のテーブルに従い自律判断する:

| 曖昧さの種類 | 判断基準 | 行動 |
|-------------|---------|------|
| 「もう少し良くして」 | コードの一般的なベストプラクティスを適用 | 命名・構造・可読性を改善 |
| 「ここ気になる」 | コメントの文脈とコード周辺を読む | 最も合理的な解釈で修正 |
| 具体性なし | 対象ファイル・行の周辺コードから推測 | 推測に基づき実装、返信で意図を説明 |
| 複数解釈が可能 | プロジェクトの既存パターンに合わせる | 既存コードとの一貫性を優先 |
| 意味不明 | 文脈を最大限読み取る | 最善の解釈で実装、返信で解釈を明記 |

**返信では必ず自分の解釈を明記する。** 誤解があればレビュアーが再指摘できるようにする。

## 冪等性の保証

2 回実行しても安全な設計:

1. **コミット前に差分確認:** `git diff` で実質的な変更がなければコミットしない
2. **返信前に既存返信確認:** 同じコメントに既に返信がないか確認してから返信
3. **テストは毎回フル実行:** キャッシュに頼らない

```
冪等性チェック:
  git diff --cached --quiet → 変更なし → コミットスキップ
  既存返信あり → 返信スキップ
  テスト → 毎回フル実行（スキップ不可）
```

## よくあるミス

| Mistake | Fix |
|---------|-----|
| 一部コメントをスキップ | ステップ 2 で両ソースから取得、ステップ 8 で全件テーブル確認 |
| テスト未実行でプッシュ | ステップ 5 は飛ばせない。全コマンドパス必須 |
| ユーザーに質問する | 質問禁止。曖昧なコメントの判断ルールに従う |
| パフォーマンス的同意の返信 | "Fixed. ..." のみ。感謝・賞賛は禁止 |
| 曖昧な解釈を明記しない | 返信で必ず自分の解釈を書く |
| コミットメッセージが曖昧 | 全変更を具体的に箇条書き |
| worktree なしで変更開始 | ステップ 0 は必須。main を汚さない |
| 2 回目実行で重複 | 冪等性チェックを実行 |

## レッドフラグ

**決してやらない:**
- ユーザーに質問しようとしている → 判断ルールに従い自律実装
- 一部コメントを「軽微だから」とスキップ → 全件処理
- テスト未実行でコミット・プッシュ → ステップ 5 必須
- `git push --force` の使用 → 通常の `git push` のみ
- worktree なしで変更を開始しようとしている → ステップ 0 に戻る
- 検証証拠なしに「完了」と主張 → verification-before-completion を適用

**必ずやる:**
- 全コメントを取得（2 ソース）
- 全コメントをテーブルで報告
- CI 同等のテストを全てパス
- 各コメントに個別返信
- コミットメッセージに全変更を列挙
- worktree 内で作業

## 連携

**REQUIRED SUB-SKILL:**
- **using-git-worktrees** - PR ブランチの worktree 作成（ステップ 0 で必須）
- **verification-before-completion** - テスト・lint 結果の検証（ステップ 5・6 で必須）

**対比:**
- **receiving-code-review** - フィードバックの批判的評価に使う（本スキルは全件実装が目的）

**呼び出し元:**
- 人間パートナーが PR のフィードバック一括処理を依頼したとき
